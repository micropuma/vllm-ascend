### <font color=green>DBO 优化</font>

#### 机制概述

DBO（Dual Batch Overlap）将大 batch 切为 2 个 micro-batch，分别在两条 NPU stream 上运行，通过 GPU event 同步点让通信与计算在硬件层面并发：

```
ubatch[0] stream: [Compute]──record──→ [Comm AllGather]──wait/yield──→ [Compute]──→
ubatch[1] stream:      [Comm AllGather]──wait/yield──→ [Compute]──record──→ [Comm]──→
```

#### 触发条件

1. `enable_dbo=True`
2. `num_tokens >= dbo_prefill_token_threshold` (默认 512)
3. MoE 通信类型非 MC2
4. Padding 后第二个 ubatch 非空

#### 核心参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `enable_dbo` | False | DBO 总开关 |
| `VLLM_ASCEND_DBO_COMM_AIC_NUM` | -1 | 通信 stream 独占 Cube 核数 |
| `VLLM_ASCEND_DBO_COMM_AIV_NUM` | -1 | 通信 stream 独占 Vector 核数 (HCCL ≥16) |
| `HCCL_OP_EXPANSION_MODE` | (default) | 通信执行硬件：AI_CPU / AIV |

> 详细机制见 `testbench/MOE/dbo/dbo.md`
> PR 文档见 `testbench/docs/report/pr-doc.md`

### <font color=green>Profile</font>

#### DBO Overlap 插入点选取

以 DeepSeek-V2-Lite A2 模式为例，每层 4 个 overlap 点：

```
Layer forward:
  dbo_mla_preprocess_hook(T) → [MLA AllGather] → dbo_mla_preprocess_hook(F) → [MLA compute]
  → dbo_linear_row_hook(T) → [o_proj ReduceScatter] → dbo_linear_row_hook(F)
  → dbo_moe_prepare_hook(T) → [EP AllGather] → dbo_moe_prepare_hook(F) → [Expert compute]
  → dbo_moe_finalize_hook(T) → [EP ReduceScatter] → dbo_moe_finalize_hook(F)
```

Overlap 策略：

```
ubatch[0] MoE finalize comm  ←→  ubatch[1] MLA preprocess comm
ubatch[0] o_proj comm        ←→  ubatch[1] MoE prepare comm
```

> 详细分析见 `dbo/dbo.md` 和 `vllm_ascend/dbo/overlap_templates/deepseek.py`

#### AI_CPU vs AIV

> 启用 DBO 优化，如下两个参数需要重点配置：

- **`HCCL_OP_EXPANSION_MODE`**: `AI_CPU`（通信独立硬件，compute 快但 sync 开销大）vs `AIV`（通信与计算共享 NPU，sync 开销小但 compute 被拖慢）
- **`VLLM_ASCEND_DBO_COMM_AIV_NUM`**: AIV 模式下可通过 core 分区隔离通信与计算

**逐 Kernel 执行时间对比** (op_statistic.csv, DeepSeek-V2-Lite, DBO+FC1, compile fullgraph):

| Kernel | Core Type | AIV | AI_CPU | 慢多少 | 根因 |
|---|---|---|---|---|---|
| MoeInitRoutingCustom | MIX_AIC | 916μs | 285μs | **+221%** | Vector(token sort/permute) + Cube(score) 频繁交替 |
| MatMulV3 (MIX_AIC) | MIX_AIC | 2016μs | 1014μs | **+99%** | 混合精度 matmul，Vector 做量化/反量化 |
| MatMulV3 | AI_CORE | 594μs | 325μs | **+83%** | 虽标记 AI_CORE，数据预处理需要 Vector 格式化 |
| MatMulV2 | AI_CORE | 246μs | 174μs | +41% | 同上，矩阵小所以预处理占比低 |
| FusedInferAttentionScore | MIX_AIC | 1317μs | 1098μs | +20% | QK^T(Cube) + softmax/post(Vector) |
| GroupedMatmul | MIX_AIC | 1157μs | 1075μs | +8% | Cube 主导，Vector 段短 |
| SwiGlu | AI_VECTOR_CORE | 240μs | 250μs | −4% | 纯 Vector，同等竞争，无额外 stall |
| AddRmsNormBias | AI_VECTOR_CORE | 188μs | 187μs | −0% | 纯 Vector，同等竞争，无额外 stall |

**Step-Level 对比** (step_trace_time, 归一化 per model call):

| 指标 | AIV | AI_CPU |
|---|---|---|
| Compute per call | 196ms | **164ms** (−16%) |
| Comm exposed per call | 34ms | 47ms |
| Free/idle per call | 22ms | 38ms |
| Total per call | 252ms | 250ms |
| Overlap 率 | 73.3% (微重叠) | 61.1% (宏重叠) |
| Kernel avg wait time | 3-17μs | 40-126μs |

**根因分析**:

- **AIV 通信拖慢计算**: AIV 通信跑在 NPU Vector 核上，与 MIX_AIC kernel 的 Vector 段（数据格式化、量化、sort/permute）直接争抢资源 → Cube pipeline 频繁 stall → compute kernel 慢 17-221%
- **AI_CPU 跨域同步开销**: AI_CPU 通信跑在独立 AI CPU 核上，NPU 全部资源给计算 → compute 全速。但 NPU ↔ AI_CPU 跨域任务调度延迟 avg 126μs (P95=951μs)，通过 DBO 乒乓同步被 cascade 放大 → 所有 kernel wait time 高 5-14x

**Trade-off 总结**:

```
AIV    = "什么都跑在 NPU 上，但什么都互相拖累"
         通信拖慢计算 (pipeline stall)，同步开销低

AI_CPU = "计算和通信物理隔离，但跨域沟通代价大"
         计算全速 (−16% compute)，但每次跨域都要付 ~126μs "税"
         这个税在 DBO 乒乓中被 cascade 放大
```

> 深度分析见 `testbench/docs/report/benchmark-doc.md` 第 4 节和 `rfc/rfc-dbo-aiv-vs-aicpu-profiling-analysis.md`
